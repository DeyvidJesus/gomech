# ADR-012: PostgreSQL Migration Baseline and Persistence Transaction Conventions

**Status:** Accepted  
**Date:** 2026-08-18  
**Deciders:** Engineering team  
**Supersedes:** None

## Context

GoMech V2 is a multi-tenant SaaS platform backed by PostgreSQL. The backend is a Spring Boot
modular monolith where each module owns its persistence (tables, indexes, constraints) but shares
a single database and schema (shared-schema multi-tenancy).

To ensure high data integrity, predictable transaction boundaries, resilience against lost updates,
and isolation between modules, the engineering team needs standardized persistence conventions
enforced across all modules.

## Decision

### 1. Flyway as the Single Source of DDL Truth

All structural changes to the database **must** go through numbered Flyway migration files. The
Hibernate property `spring.jpa.hibernate.ddl-auto` is permanently set to `validate` — Hibernate
verifies the schema at startup but never modifies it.

### 2. Migration File Naming

Files follow the Flyway convention `V<version>__<Descriptive_Name>.sql`:

| Pattern | Example | Use |
|---|---|---|
| Major version | `V1__Initial_Schema.sql` | Full baseline schema DDL |
| Sequential version | `V2__Add_Optimistic_Locking_Version_Columns.sql` | Structural additions |
| Minor version | `V2.1__Add_Phone_To_Customer.sql` | Small alterations to an existing module |
| Descriptive name | English, `Snake_Case` | Always describes what changed |

Two underscores (`__`) separate the version from the description. Files already applied to any
environment **must never be modified** — Flyway validates checksums and will fail the application
start.

### 3. UUID Primary Keys

All tables use `UUID` primary keys generated by PostgreSQL's `uuid_generate_v4()` (from the
`uuid-ossp` extension). This prevents enumeration attacks via sequential IDs and ensures global
uniqueness across tenants and environments.

Java entities use `java.util.UUID` with the default `id = UUID.randomUUID()`. The database default
(`uuid_generate_v4()`) acts as a safety net for direct SQL inserts.

### 4. Timestamp Conventions

| DDL type | Java type | Default |
|---|---|---|
| `TIMESTAMP WITH TIME ZONE` | `java.time.OffsetDateTime` | `OffsetDateTime.now()` |

All audit columns (`created_at`, `updated_at`, `deleted_at`) and domain timestamps (`expires_at`,
`last_login`, `start_date`, `end_date`, etc.) use `TIMESTAMP WITH TIME ZONE` in the DDL and
`OffsetDateTime` in Java. `LocalDateTime` is **not** used for any database-mapped timestamp — it
discards timezone information and silently depends on the JVM's default zone.

Standard audit columns present on every table:
- `created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP` — set once on insert,
  `updatable = false` in JPA.
- `updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP` — updated by the application
  on each write.

Soft-deletable tables add:
- `deleted_at TIMESTAMP WITH TIME ZONE` — `NULL` means active. Unique indexes use
  `WHERE deleted_at IS NULL` for partial uniqueness.

### 5. Optimistic Locking & Concurrency Control

All mutable domain tables use optimistic concurrency control via a `version` column:

- **DDL:** `version BIGINT NOT NULL DEFAULT 0`
- **JPA Entity:**
  ```java
  @Version
  @Column(name = "version", nullable = false)
  private Long version = 0L;
  ```

#### Decision Criteria for Versioning

| Entity Type | Optimistic Locking (`@Version`) | Rationale |
|---|---|---|
| **Mutable domain aggregates** (`tenants`, `users`, `work_orders`, `quotes`, `products`, `customers`, etc.) | **Yes** | Prevents lost updates when two users edit concurrently. |
| **Append-only ledgers** (`inventory_movements`, `audit_logs`) | **No** | Immutable rows written once; no concurrent updates exist. |
| **Pure join tables** (`role_permissions`, `user_roles`) | **No** | Managed via composite PKs and parent aggregate lifecycle. |
| **Short-lived sessions** (`user_sessions`) | **No** | Inserted on login, deleted on logout/revocation; replaced rather than mutated. |

#### Conflict Resolution
When concurrent modifications collide, Hibernate throws `OptimisticLockingFailureException`.
`GlobalExceptionHandler` translates this to HTTP **`409 Conflict`** using RFC 7807 Problem Details:
- `type`: `https://gomech.com/docs/errors/concurrency-conflict`
- `title`: `Conflict`
- `detail`: `"The resource was modified by another concurrent transaction. Please refresh and retry."`

### 6. Transaction Boundaries & Conventions

1. **Application Layer Ownership:** Transactions are defined exclusively at the use case / application
   service boundary in `com.gomech.api.modules.<module>.application`.
2. **Controllers & Repositories:** `@Transactional` is strictly forbidden in `api` controllers and
   `infrastructure` repository interfaces. This is enforced mechanically by ArchUnit rules:
   - `controllers_must_not_be_transactional`
   - `controller_methods_must_not_be_transactional`
   - `repositories_must_not_declare_transactional`
3. **Read-Only Transactions:** Query-only use cases and read methods must declare
   `@Transactional(readOnly = true)`. This optimizes database connection use and instructs Hibernate
   to disable flush checks and snapshot maintenance.
4. **Write Transactions:** State-mutating methods declare `@Transactional`.
5. **Rollback Criteria:** Standard Spring rollback applies to all unchecked exceptions
   (`RuntimeException` and `Error`). If a use case declares checked business exceptions that should
   trigger rollback, it must specify `@Transactional(rollbackFor = Exception.class)`.

### 7. Indexes, Foreign Keys & Constraints

#### Index Conventions
- **Multi-Tenant Index Prefixing:** Every secondary index and unique constraint on tenant-scoped
  tables **must** lead with `tenant_id` (e.g., `CREATE INDEX idx_products_tenant_sku ON products(tenant_id, sku_code)`).
- **Soft-Delete Partial Indexes:** Unique constraints on tables with `deleted_at` must use PostgreSQL
  partial unique indexes with `WHERE deleted_at IS NULL`:
  ```sql
  CREATE UNIQUE INDEX idx_users_tenant_email ON users(tenant_id, email) WHERE deleted_at IS NULL;
  ```
- **Naming Pattern:**
  - Standard indexes: `idx_<table>_<column(s)>`
  - Unique indexes: `idx_<table>_<column(s)>` (or `idx_<table>_unique`)

#### Foreign Key & Relationship Boundaries (Module Isolation)
- **Intra-module:** Tables within the same module use PostgreSQL foreign key constraints
  (`REFERENCES <table>(id)`) and JPA `@ManyToOne` / `@OneToMany` relationships.
- **Cross-module:** Foreign keys across module boundaries are **prohibited**. A module references
  entities in another module by plain UUID fields (e.g., `UUID customerId` in `work_orders`), without
  database-level FK constraints or JPA entity relations.
- **Cascade Rules:** `@OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)` is only permitted
  within an aggregate root managing its private internal child entities (e.g., `User` -> `UserRole`).
  Cascades must never span aggregate roots or cross module boundaries.

### 8. Flyway Profile Configuration

| Profile | `baseline-on-migrate` | `validate-on-migrate` | `out-of-order` |
|---|---|---|---|
| `application.yml` (root) | `false` | `true` | `false` |
| `local` | `true` | inherited | inherited |
| `dev` | `true` | inherited | inherited |
| `staging` | `false` | inherited | inherited |
| `prod` | `false` | inherited | inherited |

`baseline-on-migrate: true` is only enabled for local/dev profiles to simplify onboarding against
existing databases. Staging and production must never baseline — the schema must be created
exclusively by running migrations from V1.

### 9. Rollback Strategy: Fix Forward

The open-source Flyway edition does not support undo migrations (`U__`). When a migration fails:

- **Local/Dev:** Drop the database (or Docker volume), fix the script, re-run.
- **Staging/Production:** Never edit the failed script. Create a new corrective migration
  (`V<n+1>__Fix_<description>.sql`). For catastrophic data corruption, use Cloud SQL
  Point-in-Time Recovery (PITR).

### 10. Automated Persistence & Architecture Testing

Three automated test suites gate persistence changes:

1. **`FlywayMigrationIT`**: Pure Testcontainers integration test validating that the entire Flyway
   migration chain applies from a blank database, creates all 19 tables, enables `uuid-ossp`, and sets
   `UUID`, `TIMESTAMPTZ`, and `version` columns properly.
2. **`PersistenceTransactionsAndConcurrencyIT`**: Spring Boot + Testcontainers integration test
   verifying transactional rollback integrity, optimistic locking collision detection, version
   incrementation, and soft-delete partial unique indexes.
3. **`ModuleArchitectureRulesTest`**: ArchUnit test suite enforcing module layering, persistence
   ownership, and `@Transactional` boundaries.

## Consequences

1. **Entity discipline:** Every JPA entity must use `OffsetDateTime` for timestamp fields and `Long version`
   with `@Version` for mutable entities.
2. **Concurrency safety:** Lost updates are prevented without pessimistic database locks, maintaining
   high throughput under concurrent load.
3. **Strict transaction boundaries:** Transaction lifecycle is predictable and isolated in the
   application layer, keeping presentation and persistence layers free of transaction management code.
4. **Module decoupling:** Because cross-module foreign keys and direct entity associations are forbidden,
   modules can evolve their internal persistence schemas without cascading breaking changes to sibling modules.
5. **Continuous verification:** Any migration error, entity-DDL type mismatch, or transaction boundary
   violation immediately fails the build and blocks CI.
